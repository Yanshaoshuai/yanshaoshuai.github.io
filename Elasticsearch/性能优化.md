## DSL优化
### 优化方法
- 对于不需要计算相关性得分的条件,应该放入filter或must_not子句中,它们都在Filter Context中执行,筛选结果会被ES自动缓存
- 对于keyword类型的精确匹配,直接使用term查询而不是match,可以跳过分词过程
- 避免使用from+size进行大量数据的翻页,应使用search_after或Scroll API
- 通过_source过滤出业务实际需要的字段,减少网络传输和序列化的开销
- 先过滤后聚合
- 避免对取值极多的字段进行terms聚合
- 避免使用*开头的wildcard查询,这会导致全量索引扫描
### 诊断工具
- Profile API:在DSL中加入"profile": true,查看每个查询子句的详细耗时,精准定位慢查询
- Slow Log: 开启索引级慢查询日志,监控生成环境中的慢查询
```json
PUT /my_index/_settings
{
  "index.search.slowlog.threshold.query.warn": "10s",    // 超过10秒记为 WARN
  "index.search.slowlog.threshold.fetch.warn": "1s",     // 取回阶段阈值
  "index.search.slowlog.level": "info"                   // 设置日志记录级别
}
```
## refresh优化
- 频繁refresh会产生大量微小的Segment,导致IO资源消耗和Merge压力,可调整refresh间隔来降低refresh频率
    ```json
    PUT /my_index/_settings
    {
    "index.refresh_interval": "30s"
    }
    ```
- 离线导入数据时禁用refresh,在进行大规模历史数据迁移或者初始化时,应该直接关闭refresh,等待数据导入完成再开启
    - 将index.refresh_interval设置为-1
    - 数据只留在IndexBuffer和Translog中,直到IndexBuffer满或者手动触发flush。
    - 导入完成后再将index.refresh_interval设置为正常值然后强制_refresh
    ```json
    //手动flush
    //手动_refresh
    ```
- 避免再Bulk中强制,强制refresh可能导致I/O阻塞降低并发能力,除非严格要求写后立即可见
    - 禁止在请求中添加 ?refresh=wait_for 或 ?refresh=true
- 增大IndexBuffer,即使refresh间隔变长,如果IndexBuffer太小,数据依然会因为撑破Buffer而被迫refresh
    - 修改 indices.memory.index_buffer_size（全局参数），默认是 JVM 堆内存的 10%，在高写入场景下可以提高到 20%~30%

## flush优化

不同于Refresh(影响可见性),flush涉及真正的磁盘fsync。优化flush的核心是减少磁盘IO压力并平衡写入吞吐与数据安全。
- 增大触发阈值,从而减少flush频率，让一次flush能够将更多的内存数据落盘,提升顺序写的效率
    - 将index.translog.flush_threshold_size 从默认的 512MB 提高到 1GB 或更高
- 增大flush周期,即使Translog没有达到阈值,ES也会定期进行flush
    - 参数: index.translog.flush_threshold_period
    - 默认值: 30分钟
- 避免频繁手动触发_flush
    ```shell
    POST /_flush 或 POST /my_index/_flush
    ```
## Translog优化
- 默认每个请求都会执行一次fsync让Translog落盘,可以设置为async，设置为异步落盘后就会根据间隔时间批量刷盘,但可能丢失最近刷盘间隔时间内的数据
    ```json
    PUT /my_index/_settings
    {
    //默认是request 每次都刷盘
    "index.translog.durability": "async",
    "index.translog.sync_interval": "10s"  // 默认5s，可根据容忍度调大
    }
    ```

## 段合并优化
- 限制合并线程的数量,默认情况下ES根据CPU核心数自动分配合并线程(Math.min(4, CPU核心数/2)),但是对于机械硬盘多线程合并会造成磁盘寻址冲突
    ```json
    PUT /_cluster/settings
    {
    "persistent": {
        "index.merge.scheduler.max_thread_count": 1
    }
    }
    ```
## 防止数据倾斜
es中数据倾斜会导致某些节点负载过高,而其他节点无所事事,最终拖慢整个集群。可从索引设计,写入路由,分片分配三个层面入手:
- 保证分片总数是节点数的整数倍,让分片能均匀分布
- 推荐使用默认文档ID作为路由键,避免自定义路由键(?routing=user_123),防止某个路由键的数据过大导致其所在分片数据过多
